Devices, the Training Loop, and Automating It

The fourth passport — device — decides where computation physically happens, and "somewhere" has real performance consequences most people get wrong the first time they benchmark it. From there: a full training loop written by hand, broken three ways on purpose, then automated with PyTorch's own framework tools to build a real text classifier.

By the end of this read, you'll be able to

  1. Move data across devices, diagnose device errors, and benchmark GPU code correctly.
  2. Hand-write a training step and debug it using the four-passports checklist.
  3. Assemble a full PyTorch pipeline — a data loader, a module, a loss function, an optimizer — as the automated version of the hand-written loop.
  4. Build a text classifier (embedding → pooling or flatten → linear) and explain the parameter trade-off between the two.

Devices and Speed

A layer can be built, shape bugs caught, memory managed, gradients trusted — but all of that computation has to physically happen somewhere. PyTorch never moves tensors across devices automatically; it's always explicit.

x_cpu = torch.tensor([1.0, 2.0, 3.0]) x_on_device = x_cpu.to(device)
default device for a new tensor: cpu after .to('cpu'): cpu
What actually happens

Moving a model to GPU with model.to('cuda') but forgetting to move the input batch produces a RuntimeError about tensors on different devices — the same passport failure met earlier, in its most common real-world form.

"GPU is always faster" is a half-truth

GPUs win on large parallel workloads, but for tiny tensors, the overhead of launching work on the GPU can cost more than the computation itself. Timing matrix multiplication across sizes shows the pattern clearly:

Matmul latency vs. matrix size
Log–log scale. On a GPU runtime, small matrices are often slower on GPU than CPU — launch overhead dominates — until size grows large enough that raw parallel throughput wins.

The naive timing bug

GPU kernel launches are asynchronous — a Python call returns control immediately while the GPU keeps working in the background. Timing without a synchronize call measures only the launch, not the computation:

start = time.perf_counter() c = a @ b # GPU kernel launch returns almost immediately elapsed_naive = time.perf_counter() - start
naive (no sync) elapsed: 279.8976 ms On a GPU, this measures only the LAUNCH time, not the actual computation -- the real work is still running in the background when the timer stops.

Without torch.cuda.synchronize() before stopping the clock, the measurement is "how long it took to queue the work," not "how long the work took." This single missing line is behind a large fraction of misleading GPU benchmarks online.

Interview question: a teammate claims their GPU code runs a matmul in 0.01ms. What's the first thing to check?
Strong answer: Whether torch.cuda.synchronize() was called before stopping the timer, and whether a warm-up run preceded timing — both are required for an honest GPU benchmark.

torch.compile(), briefly

Wrapping a function in torch.compile() traces it and fuses operations into optimized kernels, which can meaningfully speed up code that runs the same shapes repeatedly — like a training loop. It costs compilation time on the first call, so it pays off for code that runs many times, not a one-off script.

Eager vs. compiled execution, same function
In practice

GPU cost is billed by the hour whether it's fully utilized or not. A team running small-batch inference on an oversized GPU, or forgetting synchronize() in benchmarks, routinely ends up making wrong hardware decisions — over-provisioning for a workload a cheaper GPU, or even CPU, would have served just as fast.

Check your understanding

A teammate times a GPU matmul with no warm-up and no torch.cuda.synchronize(). The reported time is suspiciously tiny. Why?

GPU operations queue asynchronously: the Python call returns as soon as work is launched, not when it's finished. Without torch.cuda.synchronize(), the timer stops while the GPU is still computing, so the measured time reflects only launch overhead — a number that looks plausible precisely because it's wrong in a consistent direction.

Capstone: a Training Loop by Hand

All four passports can now be checked: shape, dtype, device, grad. The task — fit y = w·x + b to noisy data, recovering w ≈ 3 and b ≈ 2, using nothing but tensors and autograd. No nn.Module, no torch.optim. This is the engine those tools will later wrap.

for epoch in range(epochs): y_pred = w * x + b # forward pass loss = ((y_pred - y) ** 2).mean() # MSE loss loss.backward() # fills w.grad, b.grad with torch.no_grad(): # update must NOT be tracked w -= lr * w.grad b -= lr * b.grad w.grad.zero_(); b.grad.zero_() # reset -- remember accumulation!
Loss over 200 epochs (sampled)
Log scale. The loop converges to w = 3.000 (true 3.0) and b = 1.983 (true 2.0).
Reading the loop by passport

y_pred = w * x + b is a shape check — scalar times (N,) plus scalar broadcasts cleanly to (N,), matching y. loss.backward() is a grad check — it only works because w, b have requires_grad=True. with torch.no_grad(): w -= ... is grad again — the update itself must not be tracked. w.grad.zero_() matters because, without it, the next iteration's gradient accumulates onto this one.

Deeper understanding

Same architecture, same data, same forward-pass code. The only difference between "converges cleanly," "oscillates," and "explodes to infinity" is a handful of lines governing shape, grad-tracking, and one hyperparameter. This is most of what debugging a real training run actually looks like.

Symptom in the wildCheck first
Loss is nan after 3 stepsLearning rate and grad passport (Bug B pattern)

Check your understanding

Shapes, dtypes, and devices all check out, but the loss becomes inf within the first few steps and never recovers. Most likely cause?

Rapid divergence to inf within a handful of steps — after shape, dtype, and device are already ruled out — is the signature of a learning rate that's too large: each update overshoots the minimum by more than the previous step, exactly like Bug B. A missing requires_grad would prevent learning entirely (never explode); a missing zero_grad() produces oscillation and gradual drift, not a fast blow-up.

Hand-written vs. automated

Same four passports underneath — shape, dtype, device, grad — just automated:

Hand-written
for epoch in range(epochs): y_pred = w * x + b loss = ((y_pred-y)**2).mean() loss.backward() with torch.no_grad(): w -= lr * w.grad b -= lr * b.grad w.grad.zero_(); b.grad.zero_()
Framework version
for xb, yb in train_loader: pred = model(xb) loss = criterion(pred, yb) optimizer.zero_grad() loss.backward() optimizer.step()

DataLoader replaces manual batching; model(xb) replaces w*x+b; optimizer.zero_grad()/.step() replace the manual .grad.zero_()/w -= lr*w.grad block. What didn't change: loss.backward() is identical — autograd doesn't care whether it's called inside a framework or by hand.

From Text to Tensors

The framework can automate the loop, but it still needs numbers to loop over. A neural network only understands numbers, so text goes through three steps, in order.

1. Tokenize
word → id
→
2. Pad
fixed length
→
3. Embed
id → vector

Tokenizing gives every word a number, so "the mouse ran" becomes [5, 23, 11]. Padding makes every example the same length for batching — filler zeros for short sequences, truncation for long ones. Embedding turns each id into a small list of learned values capturing how that word tends to be used — the same lookup-table idea as the linear layer, just applied to words: nn.Embedding turns a (B, T) integer tensor into a (B, T, D) float tensor.

Out-of-vocabulary (OOV)

Real text always contains words a tokenizer has never seen. Rather than crashing, every unknown word gets the same shared placeholder id — the standard term is OOV. The idea: "we don't recognize this word, so mark it unknown."

Vocabulary size: 351 Padded shape: (1120, 200) <- (batch, sequence_length) Example text : The music industry perhaps alters momentum, in fact basically it's gre Tokenized : [3, 154, 10, 254, 22, 57, 4, 50, 239, 9, 1]
Common misconception

"The vocabulary just grows to fit new words." It doesn't — fit_on_texts only ever runs on training data. Anything new at test time is OOV by construction. The tokenizer's vocabulary is a fixed passport, decided once, at training time.

Input (token ids) shape: (4, 200) dtype: torch.int64 Output (embeddings) shape: (4, 200, 128) dtype: torch.float32 Embedding matrix shape: (10000, 128) (10,000 x 128 = 1,280,000 parameters)
In practice

The embedding matrix here is 10,000 × 128 = 1,280,000 parameters — more than the rest of a small model combined. Vocabulary size is a deliberate engineering choice, not a default to leave untouched.

Check your understanding

A tokenizer fit on training text only meets the word "unprecedented" at test time, never seen before. What happens?

texts_to_sequences looks up every word and falls back to the OOV id whenever a word isn't found — every never-seen word collapses to that same single id. The sequence length is preserved: OOV words still take up a position. The vocabulary is frozen the moment fit_on_texts finishes.

A Real nn.Module: Flatten vs. Global Average Pooling

The embedding layer outputs (batch, 200, 128) float tensors. A classifier needs one prediction per sample, so that middle dimension has to collapse — there are two very different ways to do it, and the difference is a parameter-count decision made in every text or sequence model.

ApproachWhat it doesLinear layer needs
FlattenKeep every value; reshape (200, 128) into one long vector25,600 inputs
Global Average Pooling (GAP)Average across the 200 token positions128 inputs
Input features required, by approach
200× fewer inputs with Global Average Pooling.
The trade-off

Flatten keeps positional information — word 5 stays distinguishable from word 150. GAP throws position away entirely and keeps only "what showed up, on average." Neither is strictly better: it's a trade-off between preserving structure and controlling parameter count.

BasicModel: Embedding → Flatten → Linear → ReLU → Linear → Sigmoid

Embedding(10000, 128, padding_idx=0)→ (B,200,128)
Flatten→ (B,25600)
Linear(25600 → 64) + ReLU→ (B,64)
Linear(64 → 1) + Sigmoid→ (B,1)

Total parameters: 2,918,529

Interview question: the Linear(25600, 64) layer alone has 1.6M parameters. Replacing Flatten with GAP cuts that down — what's lost?
Strong answer: Position. Flatten preserves where in the sequence something happened; GAP preserves only whether it happened, averaged across the sequence. For tasks where order matters ("not good" vs. "good, not"), that loss can hurt accuracy; for tasks driven mostly by which words appear at all, GAP's efficiency usually wins.

Check your understanding

Embedding output is (batch, 200, 128). Model A applies Flatten; Model B applies x.mean(dim=1) (GAP). Which statement is correct?

Flatten reshapes (200, 128) into one 25,600-length vector (200 × 128), keeping every value; GAP averages across the 200 positions, collapsing to just 128 values. The 200 positions get averaged away — not preserved as a size-200 output.

  • Device is explicit, always. PyTorch never moves a tensor for you.
  • Benchmark honestly. Warm-up runs and synchronize() are not optional on GPU.
  • A hand-written loop and a framework loop are the same four passports — the framework just automates the bookkeeping.
  • A tokenizer's vocabulary is frozen at training time — anything new at test time is OOV by construction.
  • Flatten vs. GAP is a real trade-off between preserving position and controlling parameter count — not a default to leave unexamined.
